Small teams: treat agent frameworks as promising, not turnkey. Before you roll an agent-based workflow into production, run three targeted pre‑deployment checks: orchestration/failure‑injection, monitor/guardrail stress tests (including adversarial and collusion checks), and cost/throughput experiments under vendor "Ultrafast" or long‑leash modes. This recommendation synthesizes vendor feature claims and demos with independent incident reporting to produce concrete tests you can run locally. (Claim 03 summary: run targeted tests and require conservative deployment if tests are inconclusive — see claims 03-1 through 03-3 below.)

What to test — three concrete pre‑deployment experiments
1) Orchestration robustness and failure‑injection (why: vendors are advertising multi‑agent orchestration)
- What to simulate: multiple sub‑agents running concurrently, a lead planner agent, and external services (APIs, file stores).
- Failure injections: crash an agent process, simulate network partitions, drop or reorder messages between agents, or throttle the planner. Observe whether the system deadlocks, retries safely, or produces inconsistent outputs.
- Metrics to capture: task completion rate, end‑to‑end latency, error/retry rates, divergence across repeated runs for deterministic inputs.
- Source support: vendor demo shows single‑prompt orchestration (Antigravity demo). Quote: “With a single prompt, Antigravity orchestrates sub‑agents.” https://www.youtube.com/watch?v=nSwmcs37Jd4 [Claim 03-1].

2) Monitor/guardrail stress tests, including adversarial and collusion checks (why: independent reports flag monitor‑AI failure and collusion risks)
- Red‑team prompts: craft prompt injections aimed at changing agent objectives, elevating privileges, or leaking secrets. Test whether your monitor rejects or flags these attempts.
- Collusion simulation: run two or more cooperating agents that exchange hidden tokens or code to achieve an action the monitor should block; check whether the monitor notices inter‑agent coordination.
- Verification checks: ensure monitors validate provenance, require out‑of‑band confirmations for sensitive actions, and log full transcripts with cryptographic integrity where possible.
- Failure modes to watch: monitor being “fooled” into allowing disallowed behavior, or monitor and agent converging on policies that circumvent controls.
- Source support: Metr testimony warns: “it poses concerns like the monitor AI being fooled by the AI agent into permitting unwanted behavior, or even collusion between the monitor AI and the monitored agent.” https://metr.org/blog/2026-09-30-chris-painter-senate-testimony/ (quoted in brief) [Claim 03-2].

3) Cost, latency, and throughput under Ultrafast / long‑leash modes (why: vendor claims that speed and longer leashes change usage patterns)
- Run load tests with the same agent workflows at standard and Ultrafast/long‑leash settings. Measure tokens/sec, API cost per successful task, and operator attention time required.
- Stress scenarios: scale many agents in parallel (start small and double), observe whether cost or latency spikes nonlinearly, and whether monitoring or billing systems remain accurate.
- Capture behavioral differences: faster responses may enable agents to check their work more, or to iterate in ways that increase total token usage.
- Source support: OpenAI Amp notes Ultrafast mode and that “the greater speed changes how people use agents.” https://openai.com/index/amp-beyond-coding (quoted in brief) [Claim 03-1].

Conservative rollout and guardrails
If these tests are inconclusive or reveal risks, do not perform broad autonomous rollouts. Require human‑in‑the‑loop gates for sensitive actions, tight observability (complete logs, transaction tracing), rate limits, and explicit rollback plans. This aligns with the briefed inference: “if tests are inconclusive or reveal risks, avoid broad autonomous rollouts: deploy conservatively with human‑in‑the‑loop, tight observability, rate limits, and rollback plans.” Supporting passages: OpenAI Amp’s description of agents getting a “longer leash” and Metr’s call for better public visibility into effectiveness of restrictions. Links: https://openai.com/index/amp-beyond-coding and https://metr.org/blog/2026-09-30-chris-painter-senate-testimony/ [Claim 03-3].

Limitations and uncertainty
- What’s verified vs. claimed: the quoted passages above are vendor claims (OpenAI, Antigravity demo) and an independent policy/incident report (Metr). They justify why tests are needed but do not provide third‑party benchmarks or reproducible test suites.
- Missing data: the brief includes no independent cost numbers or standardized benchmarks. You must measure cost and failure rates in your environment.
- Counterargument: a small team may argue that testing overhead is heavy. That’s true — but the independent reporting of monitor and collusion incidents means risk is non‑trivial; the cost of a conservative test plan is often far lower than a misconfiguration or misbehavior incident at scale.

Bottom line (actionable): before production, implement the three tests above, integrate human gates and observability, and only loosen constraints after repeatable, documented passing conditions.
